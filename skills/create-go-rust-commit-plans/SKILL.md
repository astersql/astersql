# 创建 Go 逐提交严格对齐 Rust 计划

把用户指定的 Go 提交集合拆成“一条 Go commit 对应一个 Rust 对齐任务”的中文实施计划。这里只创建计划，不修改 Go、Rust、测试、构建文件或 Git 历史。

开始时说明：`我正在使用 create-go-rust-commit-plans 技能创建 Go 逐提交严格对齐 Rust 计划。`

## 组合规则

先完整阅读 `./skills/create-task-plans/SKILL.md`，沿用其中对 `plan.md`、`prompt.md`、编号任务、批次、Cargo 共享槽位和自我审查的要求。本技能是其专项约束；发生冲突时，以本技能和仓库根 `AGENTS.md` 为准。

同时读取：

- 仓库根 `AGENTS.md` 与 `PLANS.md`。
- 用户给出的来源分支、提交范围、合并提交或提交清单。
- 用户指定的示例任务；未指定时可参考 `.plans/2026-10-01-Go逐提交严格对齐Rust-demo/` 的任务结构，但不得复制其中的生成脚本或附加产物。
- 目标模块的 `doc.go`（存在时）、最近的 Go/Rust 实现、工厂接线、独立 Rust 测试和 Cargo manifest。
- DDL 任务额外读取 `docs/agents/ddl/README.md`。

代码导航优先使用 `./skills/rustcodegraph/SKILL.md`；未索引内容、Git 差异、文档和配置使用 `git`、`rg` 与文件读取。

## 唯一允许的输出

在用户指定的计划目录中只创建：

```text
plan.md
prompt.md
1-提交-<短SHA>-严格对齐.md
2-提交-<短SHA>-严格对齐.md
...
```

除上述 Markdown 文件外，不生成任何文件。特别禁止生成依赖图、文件冲突图、可视化、事实缓存、来源清单、调度数据和生成/检查脚本，包括但不限于 `.json`、`.tsv`、`.mmd`、`.html`、`.py`、`.dot`、`.svg`、`.DS_Store`。不要创建 README、references、assets 或临时副本。

如果目标目录已经有其他文件，不删除、不覆盖、不整理它们；只按用户要求创建或更新上述允许文件。保留用户和其他任务的现有改动。

## 来源提交集合

1. 用 Git 验证用户指定的完整 SHA、父提交、提交标题、拓扑顺序和实际 diff；不得根据短 SHA、文件名或旧计划猜测。
2. 普通范围默认按祖先到后代的拓扑顺序列出。合并提交差集必须明确比较哪一个父提交、共同祖先或可达集合，不能自行选择含义不同的范围。
3. 一条来源 commit 对应一个编号任务，不合并多个 commit，也不把一个 commit 拆成多个编号任务。大提交在同一任务中按函数或行为分段，允许后续执行会话续接。
4. 删除纯粹无关的非 Go 提交前必须有 diff 证据。若提交不直接修改 Go，也要在对应任务中核查它是否影响 Rust、生成链、构建元数据或测试意图；有证据确认无 Rust 影响时可作为独立核查任务完成，不能强造代码变更。
5. 任务文件必须记录完整来源 SHA、完整父 SHA、原始标题、全部来源变更路径和关键 Go 差异入口。

来源范围不明确、Git 对象不存在或存在多种不等价解释时停止生成并向用户询问；不要产出带猜测的计划。

## 严格对齐范围

每个任务只负责对应 Go commit 的增量、验证该增量不可缺少的最小局部接线和原测试意图：

- 先核对当前 Rust 已有实现，复用正确能力，只补缺失或偏离；不得为了“统一”而重写已经等价的实现。
- 每项计划中的生产修改都必须能映射到该 commit 的具体 Go 差异，或说明它为何是验证该增量不可缺少的局部接线。
- 不递归补建完整子系统、其他提交、通用基础设施或所有调用链缺口。“会被调用”“现有实现不完整”“未来可能需要”不构成扩域依据。
- Go 条件顺序、错误身份、数据形状、状态转换、事务、并发、副作用和原测试分支都属于对齐内容；禁止桩实现、空样例、仅编译通过或删减逻辑的 Rust 简化版。
- 后续 commit 撤销或替代本提交行为时，任务要求记录完整后续 SHA、源码去向和仍保留的行为；不恢复已撤销逻辑，也不吞并替代提交的全部实现。
- 不属于当前 commit 的既有缺口写入任务的“范围外建议”，不把它作为当前任务阻塞项，也不规划实现。
- 外部 Rust 依赖必须按 `AGENTS.md` 在独立上游仓库移植、提交和打 tag；本计划不得提出 vendor、third_party、本地复制或 `[patch]` 本地覆盖。

## 计划文件

`plan.md` 只保留整个提交集合共享的目标、精确来源范围、范围外、已验证假设、设计决策、架构约束、对齐原则、状态语义和总体验证策略。它是只读总指南，不列逐任务步骤、进度、任务清单、依赖图或动态状态。

编号任务是唯一进度来源。只使用：`未开始`、`进行中`、`已完成`、`已阻塞`。不要使用“已完成，待回归”或“核查完成”。完成后保留编号任务作为覆盖证据，不要求删除任务文件；除非用户明确要求，否则计划和执行提示不得要求提交 Git。

`prompt.md` 必须与编号任务一一对应，按安全批次提供可直接复制到独立会话的中文提示。提示要求执行者：

- 使用 `./skills/do-task-plans/SKILL.md` 执行具体编号任务。
- 先阅读只读 `plan.md`、编号任务和仓库说明，不修改 `plan.md`。
- 只处理该 commit 的增量和最小必要接线，不因阻塞扩大成其他提交或完整子系统。
- 逐项维护 Go→Rust 覆盖记录，取得本任务要求的当前验证证据。
- 完成时保留任务文件并更新为 `已完成`；真实缺少本提交行为、必要验证、用户决策、权限或外部状态时更新为 `已阻塞`。
- 报告变更文件、验证 profile、风险、确切命令、退出码、有效测试数量和未验证项。

Rust/Cargo 任务还必须按 `create-task-plans` 的格式，在编号文件内写完整“Cargo 共享槽位规则”，并在对应提示中写读取该规则的短句；不要把完整槽位规则重复粘贴到 `prompt.md`。

## 编号任务结构

每个 `N-提交-<短SHA>-严格对齐.md` 至少包含：

1. 标题、批次、依赖批次、状态、目的、来源 commit/父 commit/标题和预计会话范围。
2. “提交对齐范围硬约束”：明确单 commit 增量、最小局部接线、不得递归扩域及后续撤销/替代规则。
3. “文件”：完整 Go 来源路径、构建/生成元数据，以及经仓库搜索确认的现存 Rust 候选、独立测试和 Cargo manifest。候选不等于必须修改，不凭路径相似创建重复实现。
4. “上下文”：必须读取的包契约、真实入口、工厂接线、helper、调用方和仓库专项规则。
5. “Go 变更定位清单”：从真实 diff 提取的函数、类型、常量、测试入口和行为分支，只作为继续阅读完整上下文的入口。
6. “测试计划”：逐项覆盖生产变化和 Go 测试意图；缺失行为先取得真实红灯再修复，已等价行为用当前绿灯证明，不人为回退制造失败。
7. “步骤”：验证提交事实和后续去向、建立逐项覆盖表、核对生产接线、红绿修复、格式化、聚焦验证、自审和 Ready 检查。
8. “验证”：确切的 `git show`/`git diff` 来源命令、拥有 crate 的聚焦测试、适用的 Ready 命令和明确成功信号。零测试、全部 ignored 或编译失败不算行为证据。
9. “完成”：只在全部 commit 增量及测试意图有证据时完成；范围外建议不阻塞，必要行为或必要验证缺失必须阻塞。
10. “Go 到 Rust 覆盖记录”：执行时按 Go 位置/条件与顺序/错误与副作用/测试意图 → Rust 真实符号及入口 → 已有、修复或后续替代 SHA → 测试输入输出、命令、退出码和数量逐项填写。
11. `Progress`、`Surprises & Discoveries`、`Decision Log`、`Outcomes & Retrospective`，满足 `PLANS.md` 对活跃 ExecPlan 的要求。
12. “范围外建议”：只记录与当前 commit 无关但执行时可能观察到的缺口，并明确不影响本任务完成状态。

Rust 单元测试必须规划在独立测试文件，尽量与 Go 测试逻辑等价；修改 Rust 生产代码时要求保留 PingCAP Apache License，并在真正可用后按 `AGENTS.md` 添加 `// Copyright 2026 AsterSQL.`。Rust 改动后先运行 `cargo fmt --all`。

## 批次与依赖

只把真实依赖写入任务和 `prompt.md`，不另建图文件：

- Git 父子顺序本身不是 Rust 业务依赖。
- 共享候选写入文件按来源顺序串行；无写入交集的任务仍须核查真实类型、接口、行为依赖和共享可变验证资源。
- 同批任务不能争用同一源码文件、Cargo manifest/lock、生成输出、failpoint、playground、格式化或 lint 窗口。
- `cargo fmt --all`、`make lint`、Bazel prepare、根 manifest/lock、全局 failpoint 和共用 playground 需要独占窗口时，在相关任务中明确写出。
- 每批最多 10 个任务。不能证明可并行就提高批次，不用依赖图或调度 JSON 代替任务内的文字依据。

## 验证设计

- Bug fix 或行为变化必须规划回归测试，并要求修复前失败、修复后通过；已存在等价 Rust 行为时说明红灯不适用并取得当前行为证据。
- 只选择受该 commit 影响的最小测试面和仓库按变更类型要求的交付检查。全仓测试、其他 commit 回归、无关 RealTiKV/集群/性能测试不能成为默认完成条件。
- 根据 `AGENTS.md` 和 `docs/agents/testing-flow.md` 判断 failpoint、集成记录、RealTiKV、Bazel prepare；禁止规划 `make bazel_lint_changed`，除非用户明确要求。
- 代码交付默认使用 Ready profile：聚焦行为测试、`cargo fmt --all`、`cargo fmt --all -- --check`、`make lint`、`git diff --check`；生产接线变化再加入实际 NextGen 编译入口。纯文档、测试资料、构建或无 Rust 影响任务只选适用检查。
- 每条命令必须基于实际存在的 manifest、package、test target 和 feature；不得把全 crate 测试当作无法确认目标测试入口时的占位符。

## 自我审查

交付前逐项检查：

- 来源 commit 数量与编号任务数量一致，完整 SHA、父 SHA、标题和路径来自当前 Git 证据。
- 每个 Go diff 分段和原测试入口都落入对应任务，没有吞并其他 commit，也没有遗漏非 `.go` 元数据影响。
- `plan.md` 没有逐任务进度；`prompt.md` 覆盖每个任务且路径、批次、依赖与编号文件一致。
- 每个任务都说明实际 Rust 候选、独立测试文件、Cargo 所有者、红绿或当前绿证据、Ready 检查和完成门槛。
- 并行批次不存在已知文件写入、真实能力依赖或共享验证资源冲突。
- 目标目录中新生成或修改的文件只有 `plan.md`、`prompt.md` 和编号任务 `.md`；没有依赖图、脚本、缓存或其他附加物。
- 无 `TBD`、`TODO`、省略号式占位、虚构路径、虚构符号、虚构命令或“同前一任务”之类非自包含描述。

## 交接

简短报告计划目录、来源 commit 数量、编号任务数量、批次数，以及实际创建或更新的允许文件。明确说明未生成依赖图、脚本或其他附加产物，并推荐下一步从 `prompt.md` 按批次执行。
