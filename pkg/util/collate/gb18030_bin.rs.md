# `pkg/util/collate/gb18030_bin.rs`

## 文件定位

[目标源码](gb18030_bin.rs)实现 MySQL/TiDB 名为 `gb18030_bin` 的二进制排序规则，属于 Cargo crate `astersql-util-collate`。crate 入口 `pkg/util/collate/lib.rs:49-51` 将它声明为 `gb18030_bin` 模块并公开重导出；核心工厂 `pkg/util/collate/collate.rs:175-188` 在新排序规则开启时把名称 `gb18030_bin` 映射为 `gb18030BinCollator`。按字符集元数据，`gb18030_bin` 的 ID 是 249，采用 `PAD SPACE` 语义（`pkg/parser/charset/charset.rs:260,621`）。

它位于 SQL 字符串比较、排序、分组及索引 key 生成所依赖的 collation 层，而不是 SQL 执行入口。调用者通常通过 `Collator` trait 或 `GetCollator`/`GetCollatorByID` 获得 trait object，不直接依赖本文件的私有编码函数（`pkg/util/collate/collate.rs:89-118,212-245`）。

## 核心职责

- 将 Unicode 字符逐个转换成 GB18030 字节，并按转换后的字节字典序完成 `Compare` 或生成排序 `Key`（`gb18030BinCollator::Compare`、`KeyWithoutTrimRightSpace`）。
- 实现 `PAD SPACE`：常规比较和 `Key`/`KeyBytes` 忽略末尾 ASCII 空格；`KeyWithoutTrimRightSpace` 是显式保留尾空格的入口。
- 优先使用仓库的 Unicode→GB18030 映射表，保持 GB18030-2022 定制映射与 Go `NewCustomGB18030Encoder` 一致；映射表未覆盖的字符才交给 `encoding_rs::GB18030`（`encode_char`）。
- 为 Go 字符串可含任意字节而 Rust `str` 必须是 UTF-8 的差异提供原始字节入口：`CompareBytes` 和 `KeyBytes` 逐段解码，非法 UTF-8 字节稳定替换成 `?`（0x3F）。
- 返回复用 `binPattern` 的字节级通配符匹配器，使 `gb18030_bin` 的 LIKE 匹配不做大小写或重音折叠（`gb18030BinPattern`）。

## 主要符号

- `pub struct gb18030BinCollator`：无字段、可 `Default` 构造的排序规则实现。其公开能力来自 `Collator` trait；空结构体表明实例自身不保存编码器状态。
- `fn encode_char(ch: char) -> Vec<u8>`：单字符编码核心。先查 `parser_charset::unicode_to_gb18030()`；命中时用 `convert_u32_to_bytes` 输出去前导零的大端字节，否则使用 `encoding_rs::GB18030.encode`。编码器报告错误时返回单字节 `?`。
- `impl Collator for gb18030BinCollator`：实现 `Compare`、`CompareBytes`、`Key`、`KeyBytes`、`ImmutableKey`、`KeyWithoutTrimRightSpace`、`MaxKeyLen`、`Pattern`、`Clone` 和 `as_any`。
- `fn encode_bytes(value: &[u8]) -> Vec<u8>`：原始字节入口的共享转换器。它用 `decodeRune` 前进索引；非法 UTF-8 每次消费一个字节并追加 `?`，合法字符调用 `encode_char`。
- `fn compare_encoded_bytes(a: &[u8], b: &[u8]) -> i32`：分别编码两侧后用 `Vec<u8>::cmp` 比较，并将结果规范化成 -1、0 或 1。
- `pub struct gb18030BinPattern { inner: binPattern }`：持有编译后的字节级 pattern 状态；`Compile` 与 `DoMatch` 原样委托给 `binPattern`。

文件没有模块级可变常量、枚举、条件编译项或额外 trait 定义。

## 执行流程

1. 名称或 ID 查找经 `GetCollator`/`GetCollatorByID` 进入 `new_collator`，`gb18030_bin` 分支构造无状态的 `gb18030BinCollator`（`pkg/util/collate/collate.rs:175-188,212-245`）。
2. `Compare(&str, &str)` 先用 `truncateTailingSpace` 删除两侧尾部 ASCII 空格，再同步迭代两侧 Unicode scalar value。每对字符分别经 `encode_char` 转为 GB18030 字节并立即比较；首个不同字符决定结果。一侧先耗尽时较短侧更小，两侧同时耗尽则相等。
3. `Key(&str)` 先裁尾空格，再调用 `KeyWithoutTrimRightSpace`；后者把每个字符的 GB18030 编码顺序拼接。`ImmutableKey` 直接复用 `Key`，仍返回新 `Vec<u8>`。
4. `CompareBytes`/`KeyBytes` 先用 `truncateTailingSpaceBytes` 裁掉尾部 0x20。随后 `encode_bytes` 用 `decodeRune` 顺序处理原始字节；合法 UTF-8 转入 `encode_char`，非法字节输出 0x3F。比较入口再比较完整编码结果。
5. `MaxKeyLen` 以 Unicode 字符数乘 4，利用 GB18030 单字符最长四字节这一上界。它是容量/长度估算，不生成实际 key。
6. `Pattern` 创建独立的 `gb18030BinPattern`；`Compile` 把 pattern、转义字节编译到内部 `binPattern`，`DoMatch` 对目标字符串执行字节级匹配（`pkg/util/collate/bin.rs:167-180`）。

## 数据与状态

`gb18030BinCollator` 是零大小、无内部可变状态的类型。每次编码都返回新的 `Vec<u8>`：`encode_char` 对单个字符分配编码缓冲，`KeyWithoutTrimRightSpace` 再收集所有字节；`encode_bytes` 以输入长度预分配，但遇到四字节映射时仍可能扩容。`Compare` 是逐字符短路比较，而 `CompareBytes` 会先完整构造两侧编码向量，因此两条入口的临时内存特征不同。

Unicode→GB18030 的定制数据存放在 `parser_charset` 的全局只读 `LazyLock<HashMap<char, u32>>` 中（`pkg/parser/charset/encoding_gb18030_data.rs:2124-2145`）。本文件只读取它，不修改映射。`gb18030BinPattern` 则拥有一次 `Compile` 产生的 `patChars`/`patTypes` 状态；匹配只读取该状态，重新编译会替换它。

关键不变量是：常规 key 与常规比较都应用相同的尾空格裁剪和字符编码顺序；`KeyWithoutTrimRightSpace` 仅跳过裁剪，不改变编码规则；编码失败或非法 UTF-8 字节统一归一化为 0x3F。

## 错误处理与边界

该 API 不返回 `Result`。仓库定制映射未命中不算错误，会自动退回标准 GB18030 编码；只有回退编码器报告无法编码时才产生 `?`。原始字节入口遇到非法 UTF-8 时也不报错，而是每个无效字节输出一个 `?`。因此不同的无效输入可能折叠到相同 key，并比较为相等；这是与 Go 版本测试意图一致的兼容行为（`pkg/util/collate/collate_test.rs:554-585`）。

空串或全为空格的输入在常规 `Compare`/`Key` 中裁剪为空。`KeyWithoutTrimRightSpace` 保留所有尾空格。裁剪只识别 ASCII 0x20，不裁其他 Unicode 空白。`Compare` 接受 `str`，天然不可能接收非法 UTF-8；需要保存 Go `string` 原始字节语义的调用方必须使用 `CompareBytes`/`KeyBytes`。

`MaxKeyLen` 返回 `i32`，其表达式先执行 `usize * 4` 再转换；对现实字符串足够保守，但函数没有显式处理极端长度的乘法或窄化溢出。扩展时不能把它误解成实际 key 长度，ASCII/常用汉字通常少于四字节。

## 并发与资源生命周期

`Collator` 与 `WildcardPattern` trait 都要求 `Send + Sync`（`pkg/util/collate/collate.rs:89-125`）。`gb18030BinCollator` 无字段、无锁、无线程、无通道、无 I/O，也没有需要关闭的资源；`Clone` 构造另一个独立零状态实例。全局 GB18030 映射由 `LazyLock` 线程安全地初始化一次，之后只读。

`gb18030BinPattern` 的编译状态属于实例本身。通常先以可变引用调用 `Compile`，随后可通过共享引用反复 `DoMatch`；不同编译配置需要不同实例，或由调用方串行重新编译。文件不启动异步任务，也不跨调用保留临时编码缓冲，所有 `Vec<u8>` 在所有者离开作用域时释放。

## 与 Go 版本的对应关系

直接对照文件是 `pkg/util/collate/gb18030_bin.go`：

- 两版都先裁尾空格，逐字符编码后按 GB18030 字节比较；转换失败用 0x3F，并以每字符最多四字节计算 `MaxKeyLen`。
- Go 结构体持有 `*encoding.Encoder`，`Clone` 创建 `charset.NewCustomGB18030Encoder()`；Rust 结构体无字段，`encode_char` 直接查同仓库移植的 GB18030 映射表，再调用无状态的 `encoding_rs` 回退。Rust 的 `pkg/parser/charset/encoding_gb18030_data.rs` 是对 Go 定制表语义的落地。
- Go 用 `fourBytesRune` 特判若干 UTF-8 三字节私用区字符，为定制编码器准备四字节缓冲；Rust 不复制该临时缓冲技巧，而是从完整 `unicode_to_gb18030` 映射直接取得目标字节。独立测试 `gb18030_2022_private_use_keys_match_go_custom_encoder` 验证 U+E78D→`84 31 82 36`、U+E796→`84 31 83 35`。
- Go 的 `gb18030BinPattern` 匿名嵌入 `binPattern`；Rust 以 `inner` 字段显式委托，匹配语义相同。
- Go `string` 可携带无效 UTF-8；Rust 为此增加 trait 的 `CompareBytes`/`KeyBytes` 覆盖。`pkg/util/collate/collate_test.rs:554-585` 与 Go `collate_test.go:228-249` 均确认 GB18030/GBK bin 对无效字节采用 `?`，Rust 测试对 key 内容给出了更精确断言。

## 扩展指南

- 修改字符编码或 GB18030-2022 映射时，优先修改/核对 `parser_charset` 的映射数据与转换函数，而不是在本文件再建一份表；同步扩展 `pkg/util/collate/gb18030_bin_test.rs` 的定制码点样例，并与 Go `NewCustomGB18030Encoder` 输出逐字节比对。
- 修改比较规则时必须保持 `Compare`、`CompareBytes`、`Key`、`KeyBytes` 的排序一致性，并同时覆盖尾空格、空串、首个差异字符、常用双字节字符、四字节字符和非法 UTF-8。测试应继续放在独立的 `gb18030_bin_test.rs` 或现有 `collate_test.rs`，不要内嵌到生产文件。
- 修改 LIKE 行为应从 `gb18030BinPattern` 及其下游 `binPattern` 入手，并明确是否仍要求字节级而非 rune 级 `_` 匹配；这会影响与 `derivedBinPattern` 的兼容差异。
- 性能优化可考虑减少 `Compare` 中每字符 `Vec` 分配，或让字节比较流式化，但必须保留定制映射优先级、0x3F 降级和短路顺序。任何缓存都需要重新审查 `Send + Sync`、实例克隆和内存上界。
- 新增注册名或 ID 不应只改本文件，还需同步 `collate.rs::new_collator`、`parser_charset` 元数据以及注册表测试；否则实现存在但工厂不可达。
