# `pkg/parser/keywords.rs`

## 文件定位

`keywords.rs` 是 `astersql-parser` crate 内的生成式 SQL 关键字清单。文件头明确标注 `Code generated by genkeyword. DO NOT EDIT.`（`pkg/parser/keywords.rs:1`），因此这里应被视为文法生成物，而不是手工维护的业务规则源。

crate 入口 `pkg/parser/lib.rs:129-137` 将它与 token 表、Hint 表、`lexer.rs`、`misc.rs` 一起包含进私有的 `parser_impl::lexer_support`；`pkg/parser/lib.rs:199-209` 又把同一文件包含进 `digester_impl::keywords`，并通过 `pub use keywords::*` 导出该实例中的 `KeywordsType` 和 `Keywords`。最近的 `pkg/parser/Cargo.toml` 声明 crate 名为 `astersql-parser`、库入口为 `lib.rs`，没有为本文件单设 feature。

需要区分“同处词法支撑模块”和“直接查表”：主 Lexer 的标识符升级路径是 `pkg/parser/lexer.rs:235-255` 的 `Scanner::Lex` 调用 `Scanner::isTokenIdentifier`，后者在 `pkg/parser/misc.rs:1190-1232` 查询 `tokenMap`、`btFuncTokenMap` 和 `windowFuncTokenMap`；当前没有直接遍历本文件 `Keywords` 的证据。可直接确认的生产读取者是 digester。

## 核心职责

- 用 `KeywordsType` 保存一个关键字的三项稳定元数据：大写拼写 `Word`、保留属性 `Reserved`、生成器分段 `Section`（`pkg/parser/keywords.rs:27-37`）。
- 用 `RESERVED_WORDS`、`UNRESERVED_WORDS`、`TIDB_WORDS` 三个空格分隔的静态字符串紧凑保存完整清单（`pkg/parser/keywords.rs:39-49`）。
- 首次访问 `Keywords` 时，把三段数据按 `reserved → unreserved → tidb` 顺序展开为 `Vec<KeywordsType>`，保持 Go 表的顺序和下标语义（`pkg/parser/keywords.rs:51-64`）。
- 为 digester 提供不区分 ASCII 大小写的关键字成员判定：`pkg/parser/digester.rs:461-466` 遍历 `Keywords`；命中的非窗口函数词会在 `token_identifier` 中被提升为 `KEYWORD`（`pkg/parser/digester.rs:425-448`）。
- 向 crate 用户暴露完整关键字元数据；这也是 Go `pkg/parser/keywords.go` 中导出变量 `Keywords` 的 Rust 对应物。

## 主要符号

- `pub struct KeywordsType`：`Clone + Copy + Debug + PartialEq + Eq` 的纯值记录。三个字段均公开且借用 `'static` 字符串，因此复制记录不复制字符串内容（`pkg/parser/keywords.rs:29-37`）。字段名沿用 Go 的 `Word`、`Reserved`、`Section`，由 crate 级 `allow(non_snake_case)` 接受这一兼容命名（`pkg/parser/lib.rs:8-13`）。
- `const RESERVED_WORDS: &str`：保留字段。展开时所有元素得到 `Reserved = true`、`Section = "reserved"`（`pkg/parser/keywords.rs:41,60`）。
- `const UNRESERVED_WORDS: &str`：通用非保留字段。展开时得到 `false` 和 `"unreserved"`（`pkg/parser/keywords.rs:45,61`）。
- `const TIDB_WORDS: &str`：TiDB/AsterSQL 扩展段；它们同样不是 SQL 保留字，展开时得到 `false` 和 `"tidb"`（`pkg/parser/keywords.rs:47-49,62`）。
- `pub static Keywords: LazyLock<Vec<KeywordsType>>`：公开的进程级惰性表。初始化前先精确统计三段的 `split_whitespace().count()` 作为容量，再依次追加三段（`pkg/parser/keywords.rs:53-64`）。
- `fn append_section(...)`：私有展开助手，将一个 `'static` 词表按空白切分，并为每个词附上调用者给定的保留标记和段名（`pkg/parser/keywords.rs:66-79`）。它没有独立的业务分支。

文件没有 trait、enum、impl 或条件编译项；RustCodeGraph 将其识别为 7 个符号，和上述一个结构体、三个常量、一个静态量、一个函数及文件节点相符。

## 执行流程

1. `lib.rs` 编译期通过 `include!("keywords.rs")` 把定义放入目标模块；同一源码在 `lexer_support` 与 `digester_impl::keywords` 中形成各自的模块实例（`pkg/parser/lib.rs:129-137,199-209`）。
2. 某个实例的 `Keywords` 第一次被解引用或迭代时，`KeywordLazyLock` 执行初始化闭包（`pkg/parser/keywords.rs:54-64`）。
3. 闭包分别统计三个压缩词表的项目数，据此一次性预留向量容量；这避免展开过程因容量不足发生常规扩容，但仍会为最终向量分配堆内存。
4. `append_section` 先展开保留字，再展开通用非保留字，最后展开 TiDB 扩展字。`split_whitespace` 只切分分隔空白，不改变词中的下划线（`pkg/parser/keywords.rs:60-62,68-78`）。
5. 初始化完成后，所有后续访问复用同一个不可变 `Vec`。当前 Rust 回归测试把结果固定为 695 项、其中 233 项为保留字（`pkg/parser/keywords_test.rs:62-75`）。
6. 在 digester 路径中，`token_identifier` 排除限定名并先处理紧跟 `(` 的内置函数，然后调用 `is_keyword`；`is_keyword` 排除窗口函数词，再以 `eq_ignore_ascii_case` 扫描 `Keywords`（`pkg/parser/digester.rs:425-466`）。命中结果影响 SQL 规范化及摘要，而不是在此文件内产生 token 编号。

## 数据与状态

三个压缩常量和每个 `KeywordsType` 字段都引用编译进二进制的 `'static` 字符串。运行时唯一创建的可变状态是初始化闭包中的局部 `Vec`；发布到 `LazyLock` 后，`Keywords` 仅通过共享引用读取，本文件没有提供增删改接口。

顺序是接口的一部分：全局顺序固定为三段顺序，段内应按 `Word` 升序。`pkg/parser/keywords_test.rs:83-100` 逐项检查同一 `Section` 内的排序；`test_keywords` 还固定首项为保留字 `ADD`，并确认扩展词 `ADMIN` 与非保留词 `AUTO` 存在（`pkg/parser/keywords_test.rs:38-60`）。因此，新增词不仅要有正确分类，还要插入正确段内位置。

`Section` 是字符串而非 enum，合法值约束来自生成过程和测试惯例；类型系统本身不会阻止其他字符串。`Reserved = false` 同时覆盖 `unreserved` 与 `tidb`，需要区分来源时必须读取 `Section`，不能只看布尔值。

已验证的直接关系如下：

- 装配：`pkg/parser/lib.rs:135` 在 `parser_impl::lexer_support` 中包含本文件；`pkg/parser/lib.rs:204-208` 在 `digester_impl::keywords` 中包含并再导出它。
- 内部：`Keywords` 的初始化闭包三次调用 `append_section`，分别传入三段常量及相应分类参数（`pkg/parser/keywords.rs:54-63`）。RustCodeGraph 能定位 `append_section`，但对静态初始化闭包没有返回 callers/callees 边；这里以同文件源码为直接依据。
- digester：`pkg/parser/digester.rs:428-448` 的 `token_identifier` 调用 `is_keyword`；`is_keyword` 在 `pkg/parser/digester.rs:461-466` 读取 `super::keywords::Keywords`。RustCodeGraph 同样报告 `token_identifier → is_keyword → is_window_function`，而对 `Keywords.iter()` 的静态量引用由源码补证。
- 主 Lexer：`Scanner::Lex`、`getNextToken`、`getNextTwoTokens` 调用 `Scanner::isTokenIdentifier`（`pkg/parser/lexer.rs:188-255`）；后者依赖 token maps（`pkg/parser/misc.rs:1190-1232`）。本表与这些 token maps 必须在生成层面保持一致，但当前代码没有 `Lexer → Keywords` 的直接运行时调用边。

## 错误处理与边界

本文件没有 `Result`、显式错误类型或恢复分支。所有词表均为编译期固定 ASCII 内容，`split_whitespace` 对空串只会产生零项，对连续空白也不会产生空关键字；当前常量不含这些异常输入。

主要边界和失效方式是数据一致性，而非运行时 I/O：

- 错误分类会改变 `Reserved` 或 `Section` 的外部语义，但初始化本身不会报错。
- 错误排序由 `test_keywords_sorting` 捕获；数量或分类漂移由 695/233 断言捕获（`pkg/parser/keywords_test.rs:62-100`）。
- Rust 测试额外断言不包含 MariaDB 专用词 `MONITOR`（`pkg/parser/keywords_test.rs:77-81`），这是 Go 同名测试文件未覆盖的 Rust 侧兼容边界。
- 查表大小写规则不在本文件实现；digester 使用 `eq_ignore_ascii_case`（`pkg/parser/digester.rs:461-466`），而 `Scanner::isTokenIdentifier` 将 ASCII 小写转为大写后查询独立 token map（`pkg/parser/misc.rs:1204-1229`）。非 ASCII 大小写折叠不应由本表推断为已支持。
- `Keywords` 的线性成员扫描出现在 digester 中；清单规模增长会线性增加该路径的比较成本。是否需要索引结构应在性能证据出现后统一评估，不能只改本生成文件。

## 并发与资源生命周期

`std::sync::LazyLock` 保证每个静态实例在线程竞争下只初始化一次，并在初始化完成后安全发布。由于本文件被包含进两个模块，严格说是两个独立的 `Keywords` 静态实例，各自在首次访问时建立自己的向量；它们数据相同但不共享那次堆分配。

向量及其元素存活到进程结束，不需要显式关闭、取消或回收。元素只持有静态字符串切片，不拥有每个词的单独字符串分配；主要持久资源是 `Vec<KeywordsType>` 的连续存储。本文件不创建线程、异步任务、锁守卫、通道、文件、网络连接或事务，也没有可导致死锁的用户级锁顺序。

若首次初始化闭包发生 panic，行为遵循标准库 `LazyLock` 的语义；当前闭包只做容量统计、分配和无失败返回值的迭代构造，没有显式 panic 点。内存分配失败仍属于进程级分配失败边界，本文件不尝试恢复。

## 与 Go 版本的对应关系

Go 对照文件 `pkg/parser/keywords.go:19-27` 定义同名 `KeywordsType`（`Word string`、`Reserved bool`、`Section string`）和导出切片 `Keywords`。Rust 保留字段名、三种 section 字符串、元素顺序和分类值；区别是 Go 文件逐项写出 695 个结构体字面量，而 Rust 把词按段压缩成三个字符串，并在首次访问时展开。

Go 表从 `ADD` 开始，`reserved` 段之后依次是 `unreserved` 与 `tidb`，结尾为 `WIDTH`（`pkg/parser/keywords.go:27-723`）；Rust 的三个常量和三次追加保持同一布局（`pkg/parser/keywords.rs:41-63`）。Go 测试固定首项、`ADMIN`/`AUTO`、总数 695、保留数 233 以及段内排序（`pkg/parser/keywords_test.go:23-63`）；Rust 独立测试保留这些断言，并新增 `MONITOR` 排除检查（`pkg/parser/keywords_test.rs:38-100`）。

所有权模型不同：Go 导出的是可变包级 slice，Rust 导出的是 `LazyLock<Vec<_>>` 且没有公开可变访问。Rust 的 `Word`/`Section` 是静态借用，Go 对应字段是语言字符串值。两边在当前测试覆盖的观察结果上一致，但不能据此推断任意外部代码修改 Go slice 的行为在 Rust 中也可复现。

文件头称数据由 `genkeyword` 从文法生成；Rust 排序失败提示明确要求更新 `main.astergram` 并重新生成 `keywords.rs`（`pkg/parser/keywords_test.rs:92-97`），Go 提示则指向 `parser.y` 和 `keywords.go`（`pkg/parser/keywords_test.go:56-60`）。因此两端应从各自文法/生成流程同步，而不是手改其中一个生成物。

## 扩展指南

新增、删除或重新分类关键字时，应先修改相应文法/生成输入并重新生成，不要直接编辑 `keywords.rs`。安全变更至少要同时满足：

1. 将词放入正确的 `reserved`、`unreserved` 或 `tidb` 段，并保持段内字典序；若总数或保留数有意变化，同步更新 `pkg/parser/keywords_test.rs` 与 Go 对照测试的计数断言。
2. 核对独立 token maps 与文法 token 是否同步。主 Lexer 不读取 `Keywords`，只改本表可能让 digester 认为某词是关键字、而 Parser 仍把它当标识符，或反之（证据路径：`pkg/parser/misc.rs:1190-1232` 与 `pkg/parser/digester.rs:425-466`）。
3. 扩展 `pkg/parser/keywords_test.rs` 中的内容/分类回归；涉及摘要行为时同步扩展独立的 digester 测试，例如 `pkg/parser/go_merge_29_test.rs`。测试逻辑应继续放在独立 `*_test.rs`，不要嵌入生产文件。
4. 与 `pkg/parser/keywords.go` 和 `pkg/parser/keywords_test.go` 核对 Go 语义；特别检查 `Reserved`、`Section`、段内排序及 TiDB 专用词。
5. 若修改展开机制而非数据，重点保护三段追加顺序、一次初始化、静态字符串生命周期和公开字段兼容性。将 `Vec` 换成 map/set 会影响稳定顺序及可能的外部遍历行为；添加多份索引则会增加两个模块实例的常驻内存。

兼容风险主要是未加引号标识符是否仍可解析、摘要规范化是否改变以及 INFORMATION_SCHEMA/外部消费者看到的分类是否漂移；性能风险主要是首次展开的分配和 digester 的线性查找。当前文件是生成物，扩展时还应检查生成器是否会覆盖任何手工改动。
