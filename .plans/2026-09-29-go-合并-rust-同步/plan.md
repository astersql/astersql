# Go 合并同步 Rust 计划

目标：把 `ad193e964b3eb2e2f6ba81e0969442fa9231860a` 相对第一父提交的全部 Go 语义改动及测试意图同步到 Rust，并证明逐项覆盖。

范围：以 `git diff ad193e964b^1 ad193e964b -- '*.go'` 为唯一变更边界，共 1101 个 Go 路径。Go 文件的生产逻辑、新增功能、修复、测试、生成代码及重命名均须审查。逐项覆盖见 `go-change-inventory.md`；编号任务负责移植与记录证据。Go 新增目录不一定已有 Rust 同名包，需要在对应任务内按调用链确定落点。

范围外：此次合并的文档、Bazel、Go module、非 Go 资产及与 Go 语义无关的清理；本计划不直接改生产代码。

假设：本提交是双父合并，第一父 `1089ded6038ca8d2d3f32bde32fcad29bc6298b1` 是合并前本仓库基线；Rust 工作区已有同目录或邻近目录的 Cargo 包，但当前 Cargo 根文件注明机械迁移草稿未保证全工作区可构建。

## 设计决策

- 采用第一父差异，保留所有 Go 文件路径作为覆盖边界；第二父是被合并来源，不能用默认 merge diff 的空输出。
- 按 Go 所属子系统、最多八个文件且一般不超过 900 行差异分成聚焦任务；单个超大文件独立成任务。大文件须按函数或行为再细分实际实现步骤，不能把测试通过等同于全文件完成。
- 对单文件超过 900 行差异的任务，实施时先列函数/行为清单，分段分别记录失败与通过证据；若无法在一个聚焦会话完成，应在同一文件中记录未完成函数并保持 `未开始` 或 `已阻塞`，随后继续该任务，不能整体报完成。
- 对生成 Go 文件追溯生成源和 Rust 生成机制，不手工逐行复制生成物；测试文件与生产代码一起核查意图。每项若无 Rust 可移植行为，需给出代码证据和理由。
- 同一子系统任务按编号顺序推进；不同子系统按基础层、查询层、运行层、外围层分阶段并行。批次内严禁同时修改同一 Rust 文件；`cargo` 共用构建目录、Go failpoint、RealTiKV playground 和 `make lint` 等共享验证资源要串行使用，或以独立构建目录隔离。发现交叉依赖时等待上游任务完成并在任务文件记录。

## 架构说明

- Rust 在 `Cargo.toml` 工作区内按 Go 包分拆为多个 Cargo 包；任务文件给出候选清单，实施者须用 `rustcodegraph` 和源码确认真实所有者及相邻测试。
- 先读目标包 `doc.go`（若存在）；DDL 还须读 `docs/agents/ddl/README.md`。Rust 测试放独立文件，保留 PingCAP 版权，并在真正可用的 Rust 源文件顶部加 `// Copyright 2026 AsterSQL.`。
- 外部 Rust 依赖须在独立上游仓库移植、提交、打 tag，工作区只引用统一已发布 tag；不得使用本地 patch、vendor 或 third_party 副本。

## 开发策略

- 每个行为改动先写 Rust 失败回归测试，记录预期失败，再移植 Go 语义并通过聚焦测试。纯测试、生成产物或机械适配需要在任务文件说明测试驱动开发不适用的具体理由。
- 任务执行中逐个比较 Go 变更的函数、分支、错误、边界和测试，与 Rust 对应点形成覆盖记录；Rust 独有基础设施可适配，但不得删减 Go 逻辑。
- 每个编号任务只更新自身任务文件的状态或完成后删除；`plan.md` 只读。最终核对 `go-change-inventory.md` 1101 行均有对应完成证据，统一做集成回归。

## 验证与交接

- 先用 `.agents/skills/tidb-verify-profile`（若存在）选择 WIP/Ready；当前工作树未见该目录时，按 `AGENTS.md` 和 `docs/agents/testing-flow.md` 的等价最小检查执行并记录缺失。
- Go 源变更只作参考，若任务实际修改 Go import、新增顶层 Go 测试或 Bazel 元数据，必须先判断并执行 `make bazel_prepare`；不得运行 `make bazel_lint_changed`，除非用户明确要求。
- 交付逐任务记录修改文件、验证 profile、风险、准确命令及未验证项。最终进行 `cargo fmt --all -- --check`、按变更范围的 `cargo test`/`cargo check`、代码变更所需 `make lint`，并对不能运行的检查说明具体阻塞。
