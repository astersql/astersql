# Rust 慢测极限优化计划

目标：逐项复核并优化 `target/rust-test.4uY80L` 中普通任务原始耗时大于等于 1.0 秒、重型任务原始耗时大于等于 2.0 秒的唯一 Rust 测试，在保持 Go 对齐逻辑、测试规模和真实行为的前提下取得明确收益，或用证据确认已无合理的继续优化空间。

范围：按日志最大观测耗时降序覆盖 1,189 个唯一测试身份：普通任务保留 `>=1.0s`，重型任务保留 `>=2.0s`。重型任务指任务元数据标记为 `external-service`、`benchmark-harness`，或涉及 RealTiKV、DDL 状态机的任务。筛选不保护任何任务状态：`未开始`、`已阻塞`、`已完成，待回归` 和 `已完成，待回归验证` 均按相同门槛处理；已完成且已按协议删除的任务不重新创建。

范围外：普通任务原始耗时 `<1.0s`、重型任务原始耗时 `<2.0s`、7 个短时失败的 Rust 测试、Go 既有失败，以及通过删案例、缩小 Go 对齐数据规模、改用不等价 mock、放宽超时或降低 benchmark 工作量获得的表面提速。

假设：源日志 SHA-256 为 `d56cb051199f5fcfff8acb47177f2c4cae57254acb4c698a07f092874dea405c`；它来自 `make rust-test` 的 `--workspace --all-targets` 并发运行，因此不是纯 `--lib` 单元测试。1 秒/2 秒只用于任务入选；单项完成不再绑定 0.5 秒绝对线，仍需按现有脚本预热后重复五次，以排除单次抖动。

## 设计决策

- 方案一是直接按全量并发耗时改代码，速度快但会把 CPU、I/O 和共享服务争用误判成测试本身开销；不采用。
- 方案二是按 package 合并任务，文件少但违背“一项测试一个任务”，也难以给出逐项完成证据；不采用。
- 采用“一项唯一 binary/test 身份一个任务”：原始日志负责排序和分层入选，真正修改以五次预热隔离基线和剖析证据为准。
- 普通任务门槛为 `>=1.0s`；外部服务、benchmark harness、RealTiKV 和 DDL 状态机任务会消耗更多实现、环境与验证 token，门槛放宽为 `>=2.0s`。
- 任务状态不影响入选门槛；阻塞或待回归记录若低于对应门槛，同样直接移出计划。
- 正确性是硬门槛：五次测量必须精确选中测试、零失败、零超时。测量命令使用 `--max-seconds 300` 作为防失控护栏，不把它当作性能目标。
- 默认的“明显提升”安全线是相同条件下 after 相对 before 的中位数和最大值均改善至少 20%；若未达到 20%，只有在剖析证明主要可优化热点已消除，且继续优化会削弱 Go 对齐语义、真实依赖或协议/时序边界，或投入显著大于剩余收益时，才可凭完整证据完成。
- “无法继续优化”不再标记为阻塞：至少记录瓶颈分解、已尝试方案、剩余下界和拒绝继续修改的具体理由；正确性通过后可标记完成。缺少证据、测试失败、零测试或尚有明确安全热点时仍不得完成。
- 既有 `已阻塞`、`已完成，待回归` 和 `已完成，待回归验证` 记录同样适用新判据：已有五次正确性和剖析证据仍有效；若证据已证明明显提升或无合理继续优化空间，可直接按通过收口，不得因历史记录中的 0.499 秒失败重新阻塞。只有环境/依赖仍不可用、正确性未完成或证据不足时才继续保留待办状态。
- 不在计划中手工切分静态批次。1,189 个原始入选任务作为无业务前置依赖的独立工作项交给系统自动并行调度；Cargo 槽位、源码冲突和真实服务资源由调度与任务内锁规则约束。五次隔离计时仍通过仓库级性能锁保证可重复性。

## 架构说明

- `Makefile` 的 `rust-test` 使用 cargo-nextest 执行 workspace 的 `--all-targets`；`.config/nextest.toml` 的默认 profile 并行运行，`perf-audit` profile 则单线程运行。
- `tools/check/rust-test-performance.sh` 负责预热、重复测量、零测试/失败/超时检查和 TSV 证据输出；每个任务用 binary id 与完整 test name 双重精确过滤。
- 原始日志共有 1,466 项 `>=1s`、319 项 `>=2s`、53 项 `>=5s`；分层规则从 `>=1s` 集合中排除 277 个耗时在 `[1s,2s)` 的重型任务，最终保留 1,189 项。
- 2026-10-12 全量隔离复测曾观测到 755 项 `>=1s`、162 项 `>=2s`、20 项 `>=5s`；入选但隔离基线已经达标的任务，仍可按五次复核证据无代码完成。
- 热点分型是入选与剖析依据之一，不允许据此预设修改结论；普通初始化、算法/I/O、组合规模和固定等待从 1 秒起处理，重型边界从 2 秒起处理。
- 重点证据：实例计划缓存的 Go/Rust 对齐并发用例包含 2,000 条语句和 10 个 worker；统计用例显式构造 100,010 行、7 个分区；planner golden 用例常同时运行 standard/cascades。上述规模与双路径覆盖不得删减。
- RealTiKV 任务必须按 `docs/agents/testing-flow.md` 启停真实 playground 并清理；DDL 任务必须先读 `docs/agents/ddl/README.md`，验证 job、schema state、reorg、回滚和 schema sync 语义没有被性能改动破坏。
- `prompt.md` 只提供扁平任务队列，不编码人工批次或批次依赖。系统可根据实时可用会话、Cargo 1–10 共享槽位和锁状态动态调度，无需等待人工波次完成。

## 开发策略

- 每项先运行原测试取得五次隔离基线；若数据证明原日志主要是全量并发噪声且没有稳定热点，可不制造代码 diff，记录证据后完成。对于日志中的 FAIL/TIMEOUT，必须先恢复正确通过，再评估性能收益。
- 用 RustCodeGraph 查看精确测试节点、callees、callers 和 impact；在测试的 setup、fixture/load、主体、teardown 四段做临时时间分解，提交前删除诊断插桩。
- 优先消除重复且语义无关的初始化、重复解析、忙等/固定 sleep、重复磁盘往返和不必要分配；只缓存不可变数据，任何共享 Domain/Session/全局状态复用都必须证明隔离与清理。
- 不减少 SQL、case、并发 worker、行数、分区数、压缩格式、planner 模式、真实服务边界或断言；Rust 测试逻辑和生产逻辑继续尽可能对齐 Go。
- 若真实租约、网络、DDL propagation 或 benchmark 采样存在不可消除的下界，记录剖析、尝试方案和五次数据后可完成，不能通过弱化语义制造提速。
- Rust 源与测试逻辑保持分文件；真正可用的 Rust 生产代码顶部补 `// Copyright 2026 AsterSQL.`，保留原 PingCAP Apache License；外部 Rust 依赖不做本地 vendor/patch。
- Rust 代码修改后先 `cargo fmt --all`，再做精确性能验证与 `make lint`；默认不触发 `make bazel_prepare`，除非执行中实际满足 AGENTS.md 的 Bazel trigger。

## 验证与完成标准

- 每项 `before`/`after` 报告必须各精确选中 1 个测试并各包含 5 个成功 sample；失败、超时或零测试不得作为性能完成证据。
- 优先以中位数和最大值均改善至少 20% 判定明显提升；未达到时必须提供可审查的热点分解、已尝试方案、不可消除下界或继续优化会损害语义/投入产出失衡的证据。没有统一的 0.5 秒完成线。
- 每项交付必须记录实际 Cargo 槽位、绝对 `CARGO_TARGET_DIR`、命令、退出码、有效测试数量、before/after 五次耗时、改善比例或停止优化依据，以及 diff 自审结论。
- 代码任务使用 Ready profile：`cargo fmt --all`、任务内精确性能命令和 `make lint`。只做基线复核且无需源代码修改时，仍记录五次证据并按任务执行协议处理状态。
- 所有任务完成后再运行一次 `make rust-test` 做 workspace 回归并解析新日志；由于范围外仍有 7 个原始短时失败，必须逐一确认最终非零退出是否仅来自这些已记录的范围外项，不能把新的失败归为既有问题。

## 风险与边界

- 正确性风险最高：共享夹具和缓存可能泄漏 schema、session variable、全局 registry、时钟或随机状态；必须有显式 reset/teardown 证据。
- 兼容性风险中等：Go golden、DDL 状态机、TiKV/PD 真实交互和协议测试不能被 mock 替代。
- 性能风险中等：全量并发日志含争用噪声，隔离变快不保证全量墙钟时间同步下降；最终 workspace 回归用于发现该差异。
- 交付规模风险仍较高：原始范围保留 1,189 个独立任务，当前活动文件会随已完成任务继续减少；系统动态并行可消除静态批次等待，但真实 TiKV、共享源码和隔离性能锁仍会限制瞬时吞吐。
